# CVApplyr — The Fix Plan
### Code-grounded designs for the five walls · 2026-07-30

Companion to `USER_PAIN_DEEP_DIVE_2026-07-30.md`. Every design below was produced by tracing the
actual code (citations are real file:line references) and respects the standing constraints:
App.js untouched, no new dependencies, additive/idempotent migrations, admin-tunable where possible.

**The shape of the plan: two waves.**
- **Wave 1 — backend-only, deployable immediately** (no app release): kills the fake-URL scrapes for ALL existing builds, scores every match, makes the welcome bundle complete a loop, persists cover letters server-side, retries stuck résumés, notifies on fixes, opens the anonymous feed API, hardens the demo account. Users on 3.0 benefit the same day.
- **Wave 2 — the next app build (3.5)**: the classifier UX ("'finance' looks like a job type — search all jobs?"), the top-up sheet, the résumé-retry banner, assume-submitted prompt, browse-before-signup UI, update banner.

## Wall 1 · Search box → real search

**Root cause found:** the modal pre-fills the input with the literal string `https://`
(`app/(ai-hub)/index.tsx:1820`) — a user typing `plulmbing` after the prefill *builds* `https://plulmbing`,
and the dot-check at :1722 leaves it alone because a protocol already exists. Server-side,
`resolveCareersUrl` (aiHubController.js:1108–1154) **fabricates** `https://www.<word>.com/careers` from any
bare word and at :1153 returns `https://www.<slug>.com` even after every probe failed — "pakistan" →
`www.pakistan.com`. No input classification exists anywhere.

**Fix (server is authoritative, client is UX):**
1. New `server/utils/inputClassifier.js`: strip protocols whose "hostname" has no dot (kills fake URLs
   for ALL app versions); deterministic tiers — valid URL / country-city lexicon / ~150-word industry
   lexicon / Levenshtein≤2 typo suggestion; ambiguous single words → one cached flash-lite call
   (cache table via idempotent db-init migration `input_classifications`).
2. `getJobMatches`: classify before normalising. `category`/`place` → 422 `keyword_query` (NO charge);
   `typo` → 422 `did_you_mean`; `resolveCareersUrl` last resort returns null → honest `not_a_company`
   instead of a fabricated domain. New behaviour gated on `classify=1` param so old builds keep exact
   current behaviour; `force=company` lets the user override.
3. Client (build): prefill → placeholder; keyword/place → "'finance' looks like a job type, not a
   company → [Search all jobs] [Search anyway]" routing to `/(discover)` with `q` auto-run (the
   discover zero-state already offers live Google). Typo → "Did you mean plumbing?".

**Effort M · server half ships now.**

## Wall 3 · Credits that complete a loop

**Root cause:** welcome = literal `5` hardcoded at 6 grant sites (authController.js:160–177, :577,
:884, :1187, :1452, server.js:1093); a full loop costs 6 (search 3 + letter 1 + download 2); every
"not enough credits" moment is a dead-end `Alert.alert` with no telemetry and no CTA.

**Fix:**
1. `welcome_bonus` becomes a row in `ai_event_costs` (admin-tunable at runtime, floor 5); grant sites
   read `getWelcomeCredits()`. **Recommend 10** — covers search + 2 letters + download with 3 left,
   a natural purchase moment.
2. `first_download_free` toggle (also an ai_event_costs row): first-ever download costs 0, self-idempotent
   via the `first_download_free` usage row. Zero-deploy interim lever: drop `cover_letter_download`
   2→1 in the existing admin screen (live in ≤20s).
3. Telemetry: `insufficient_credits` app_event written in every server 402 branch (covers old builds)
   + client-side `TopUpSheet.tsx` replacing the dead-end alerts (build). Known limitation: the purchase
   UI lives in App.js, so the sheet shows pack prices + "Account → Credits" pointer.
4. Retro-grant for the ~26 stranded real users: admin endpoint using the existing idempotent
   `grantReward` (`user_reward_grants` idem-key makes re-runs no-ops) + the existing credits push.

**Effort S–M · everything except TopUpSheet ships now.**

## Wall 4 · No more silent failures

**Scoring (76% unscored → "0%"):** scoring is pull-only — it runs ONLY when the new build's AI-hub
screen renders a card (drainer, index.tsx:1398–1441) or for >200-role employers (Phase B). Fix:
(a) fire-and-forget `scoreEmployerJobsInBackground` right after every search completes
(aiHubController.js:3122); (b) `matchBackfill.js` worker every 10 min: free deterministic
`localSkillScore` first, one flash-lite batch for the rest, naturally idempotent via `scored_at`;
(c) no-resume users: banner "Add your résumé to see your match %" (build). Backend deploy alone
removes the 0% wall for every build.

**Cover letters:** persistence is client-side fire-and-forget (`saveJobCoverLetter` is `catch {}`) —
app killed mid-poll = letter lost, no row, no event. Fix: server upserts `job_cover_letters` itself on
generation success (pass `sourceJobId` through, reuse the upsert SQL at aiHubController.js:4487); emit
`cover_letter_failed` events on the failure path; client retry + "Already generating…" toast (build).

**Stuck résumés (users 66 & 70 — confirmed the sweeper does NOT cover them):** their errors
(`'Expected , or ] after array element'`, bare `'403 Forbidden'`) match neither RETRYABLE_SRC nor
PERMANENT_SRC → `retryable=false` → sweeper SQL never selects them. Fix: add those classes to
RETRYABLE_SRC, guard with new `retry_count` column (cap 5, additive migration), plus
`GET /resume/parse-status` + `POST /resume/parse-retry` endpoints and a `ResumeParseBanner.tsx`
("We couldn't read your résumé — tap to retry", build).

**"Your search is fixed" push:** new `employer_fix_resolved` template (category
`application_updates`), sent from `runInvestigation`'s resolve point (employerFixController.js:33–36)
via the existing `sendToUser` rail — skip user 1's sweep rows. Backend-only.

**Assume-submitted:** track harvested-answer count; on WebView close with submit-intent + ≥3 harvested
answers and no detected submit → one-tap "Did you finish applying? [Yes, I applied]" (build).

**Effort M · roughly two-thirds ships backend-only.**

## Wall 5 · The front door and reach

**Discovered:** `discoverJobs` is already null-safe for anonymous users (`getResume(null)` → noProfile
mode) — the wall is purely the `authenticateToken` middleware. And per-IP login rate-limiting
already exists (authLimiter, server.js:520). The login UI is inside App.js (off-limits) — the plan
works around it.

**Fix:**
1. **Anonymous feed, backend now**: `/api/public/discover/{jobs,facets,job/:id}` — same controller,
   anon rate-limit 120/15min. Client (build): use public paths when signed out; a `BrowseJobsCTA`
   overlay on `app/index.tsx` (the 3-line App.js re-export wrapper — editable!) shows "Browse jobs"
   to signed-out users → `/(discover)`; save/apply/letter gate on a "Create a free account" sheet.
2. **Update nudge**: `/app-config` gains `minVersion/latestVersion/updateUrl` (env-driven, backend
   now); `UpdateBanner.tsx` in HomeScreen + discover layout (build). Points at the existing
   cvapplyr.com/download redirect page.
3. **login_failed identity**: add `emailHash` (sha256, 16 chars) + `reason` to the app_events mirror —
   failed→recovered joins become measurable. Backend now.
4. **Demo hardening**: block `cvapplyrtest@gmail.com` login unless `DEMO_LOGIN_ENABLED=1`
   (⚠️ flip it ON during store reviews — Apple uses this account; blocking it mid-review = rejection).
   Backend now.

**Effort M · half ships now.**
